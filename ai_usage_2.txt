UNDERSTANDING

I did not write the Stage 2 code myself. An AI agent generated it, and I asked it to re-check its work and fix mistakes. This is how I understand it.

The compiler works in steps. The lexer reads the file as UTF-8 bytes and splits it into tokens (emoji and ASCII words). The parser builds a tree of the program, with one function per grammar rule. Then a separate semantic pass checks the program: types, whether names are declared, the number and types of function arguments, whether fields are mutable, and whether a function returns the right type. Only after that does the code generator build LLVM IR with llvmlite. The checks come first because llvmlite doesn't report a wrong function call properly.

Inside a member function, a name is looked up in this order: parameters and local variables, then the structure’s fields, then global variables.

Each structure becomes an LLVM struct type. Each member function becomes a normal function whose first parameter is a pointer to the object. A field is accessed by its index in the structure, not by its name. A member function that changes a field (directly or through another such function) is “mutating”, so it cannot be called on a constant object. Changing a field through a chain like a.b.c is allowed only if every object along the chain is mutable.

read stores the number from scanf in a temporary variable. print chooses the format by type (%d, %lld, or true/false), for an object it prints every field, and each print ends with one newline. 🪴(...) checks for overflow while the program runs and stops it if one happens.

The test runner compiles each valid program, runs it and compares its output with the expected file. For invalid programs it compares the error message.
